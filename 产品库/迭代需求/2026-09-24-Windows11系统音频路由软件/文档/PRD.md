# PRD：Windows11系统音频路由软件（AudioRouter）

## 目标与范围

承接已确认目标文档（产品库/迭代需求/2026-09-24-Windows11系统音频路由软件/文档/目标.md）。

- 一句话：Windows 11 个人自用桌面工具，把选定的一个或多个应用的播放声音与真实麦克风人声混合，送入一个虚拟麦克风设备，供聊天软件选用；本地播放不受影响，配置极简。
- 目标用户：用户本人（唯一使用者），同时使用"语音聊天软件/游戏内语音 + 音乐/视频应用"的场景。
- 明确不做（继承目标§5）：变声/混响/EQ、录音、格式转码音质增强、商业化分发、macOS/Linux/Win10- 适配、手机端。

## 方案推演与取舍

技术上有三条可行路线，对比如下（Tier 2 必要对比）：

| 维度 | 路线A：脚本化配置 Voicemeeter | 路线B：自研控制层 + 复用成熟虚拟设备（推荐） | 路线C：全自研（含虚拟音频驱动） |
|---|---|---|---|
| 按应用粒度取声 | 依赖 Voicemeeter 混音器，按应用区分能力弱 | Windows 11 WASAPI 进程环回（Process Loopback）原生按 PID 取声，精确 | 同B |
| 独立音量控制 | 只能控总通道，不满足"每源独立音量" | 每源软件混音，精确满足 | 同B |
| 虚拟麦克风 | 复用 Voicemeeter 虚拟设备 | 复用 VB-CABLE 等成熟虚拟声卡（个人免费使用） | 需自写内核态驱动 |
| 复杂度/风险 | 低开发量，但被他人软件 UI/版本绑架，正是用户"太难用"的现状 | 中等：纯用户态开发，无内核代码 | 极高：驱动开发+签名（个人工具不现实） |
| 稳定性 | 随 Voicemeeter 升级漂移 | 虚拟声卡久经考验；控制层自控 | 自担全部风险 |
| 结论 | 否——不解决"太难用"真问题 | **采纳** | 否——成本收益严重失衡 |

最终架构（路线B）：用户态控制程序 = 进程枚举与音频捕获（WASAPI Process Loopback）+ 每源音量乘法混音 + 真实麦克风采集混入 + 输出写入虚拟麦克风设备；首次运行引导安装/检测虚拟声卡驱动。

## 最终方案

- 形态：Windows 11 桌面应用（单窗口），常驻系统托盘。
- 音频链路：`[网易云 PCM ×音量A] + [抖音 PCM ×音量B] + … + [真实麦克风 PCM] → 混音 → 虚拟麦克风设备`；本地扬声器链路完全不动（声音照常从默认输出设备出去，本工具只"旁路复制"一份）。
- 关键决策：
  - 按应用取声用 WASAPI Process Loopback（Win11 原生支持，无需 hook、无需驱动）。
  - 虚拟麦克风复用 VB-CABLE（成熟免费虚拟声卡），本工具负责自动检测、一键引导安装与校验，不自行开发驱动。
  - 聊天软件侧唯一需要用户做的事：把输入设备切到虚拟麦（首次引导带截图指引，之后不再变）。

## 功能与业务规则
| 功能 | 说明 | 规则 |
|---|---|---|
| 应用音源枚举 | 下拉复选框列出所有具备音频输出（扬声器）权限的应用，仅显示应用名称 | 只列有音频输出能力的应用；下拉收起时显示已勾选应用名摘要；每3秒刷新 |
| 已共享应用栏位 | 下拉框下方栏位逐行展示已勾选的应用：应用名、当前音频电平、音量调节滑块 | 每行电平条实时反映该应用当前声音大小；取消勾选后对应行移除；容器最大显示 3 行，超出部分纵向滚动；空态显示"勾选上方应用开始共享" |
| 多源选择 | 每个应用一个"共享"开关，可同时开启多个 | 开关即"该应用声音进入虚拟麦"；与本地播放互不影响 |
| 每源独立共享音量 | 每个已共享应用一条音量滑杆（0–100%） | 只影响"发给好友的音量"，不影响本地听到的音量；默认80%；拖动实时生效（延迟≤200ms） |
| 麦克风混入 | 真实麦克风人声始终混入虚拟麦 | 人声不做音量处理（保持原样）；无麦克风/麦克风被占用时明确提示 |
| 物理麦克风选择 | 窗口底部下拉框选择人声来源的物理麦克风设备 | 默认选系统默认麦克风；切换实时生效（不断流）；无可用设备时下拉框置空并提示 |
| 虚拟麦克风设备 | 对系统呈现为一个标准录音设备"AudioRouter 虚拟麦" | 启动时自动检测虚拟声卡：未装→引导安装；装了但被禁用→提示启用路径 |
| 共享总开关 | 开关行文案随状态切换："开启共享"/"关闭共享"，无附加描述 | 开启=勾选应用的声音混入虚拟麦；关闭=虚拟麦里只剩人声；本地一切不变；托盘图标同步状态 |
| 首次配置引导 | 三步引导：①装虚拟声卡 ②聊天软件输入设备选"AudioRouter 虚拟麦" ③完成 | 仅首次出现；每步带状态检测（装好/选对才亮下一步）；目标≤5分钟 |
| 托盘常驻 | 最小化到托盘，开机可选自启 | 双击托盘恢复窗口；退出=停止共享并还原（虚拟麦静音，仅人声） |
| 状态显示 | 主界面顶部显示：虚拟麦状态、当前共享源数（电平类信息按应用粒度展示在已共享应用栏位，不设全局输出电平条） | 已共享栏每行电平条实时反映应用声音，方便确认"有没有声音出去" |

## 异常场景
| 场景 | 处理 | 提示 |
|---|---|---|
| 虚拟声卡未安装/被卸载 | 停止共享，弹引导 | "未检测到虚拟声卡，点击开始安装（约1分钟）" |
| 真实麦克风拔出/被占用 | 共享继续（音乐仍可共享），人声缺席 | "麦克风不可用：好友将听不到你的说话声" |
| 被共享的应用退出 | 该源自动移除（30秒缓存期内重开则恢复原音量设置） | 列表移除该行；不弹窗打扰 |
| 所有输出设备切换（如插拔耳机） | 重新绑定 loopback 端点，共享不断流 | 无感；失败才提示"音频设备变化，请重开共享" |
| 采样率/缓冲异常导致爆音 | 自动重协商格式；连续失败降级为暂停该源 | "抖音声音异常已暂停，点击重试" |
| 系统睡眠/恢复 | 恢复后自动重连全部链路 | 失败则提示并一键"重新连接" |
| 驱动安装需要管理员权限 | 引导中请求 UAC；拒绝则停在第一步 | "需要管理员权限安装虚拟声卡" |

## 验收标准
| 编号 | Given | When | Then |
|---|---|---|---|
| AC-01 | Win11 电脑正在语音连麦，网易云在播放，抖音在播视频，聊天软件输入设备已选"AudioRouter 虚拟麦" | 仅开启网易云的共享 | 好友端听到人声+网易云声，听不到抖音声；本地听感不变；用户说话不受影响 |
| AC-02 | 网易云与抖音均已共享 | 仅拖低抖音源音量滑杆至0 | 好友端抖音声消失，网易云与人声不变；本地听感不变 |
| AC-03 | 任意共享进行中 | 点击共享总开关关闭 | 好友端音乐声消失、人声正常；本地播放不受影响 |
| AC-04 | 全新安装后首次使用 | 按三步引导操作完成 | 首次配置≤5分钟达到共享效果（目标值，实测校准） |
| AC-05 | 共享持续开启 | 连续使用≥1小时 | 无回声/啸叫、无爆音、无内存持续增长、无可感知额外延迟 |
| AC-06 | 虚拟声卡已装且正常 | 启动本软件 | 主界面显示"虚拟麦就绪"，无需任何手动配置 |
| AC-07 | 网易云共享中 | 网易云被关闭 | 该源从列表移除且不弹窗；重开后30秒内恢复原音量设置 |
| AC-08 | 存在多个物理麦克风设备 | 在底部下拉框切换麦克风 | 人声来源实时切换，共享不中断；虚拟麦输出立即来自新设备 |

## 方案自检（三视角）
| 视角 | 检查问题 | 结论 |
|---|---|---|
| 价值 | 是否仍在解决目标第3段的真问题，范围未扩张 | 通过。三条真问题逐一对应：声音"递"不出去（虚拟麦混合链路）、现有工具太难用（装好即用+三步引导+应用粒度勾选，隐藏全部路由概念）、共享音量没法单独控制（每源独立滑杆且只作用于发送侧）。无范围扩张：未加入目标之外的特效/录音等功能 |
| 实现 | 流程/规则/数据/依赖/异常是否成立 | 通过。核心依赖两项已确认可行：Win11 WASAPI Process Loopback 原生支持按进程取声；VB-CABLE 提供成熟虚拟声卡。混音为用户态 PCM 乘加运算，无技术不确定性。异常场景覆盖驱动/设备/应用退出/睡眠等7类，均有处理与提示。遗留确认项：具体聊天软件与抖音客户端形态（目标§6待确认项，实现阶段实测） |
| 质量 | 结果是否可观察、可验证 | 通过。7条验收标准全部可观察可核验（好友端听感、本地听感、列表行为、时间指标），与目标§7验收基线一一对应；输出电平条提供日常自检手段 |
